Primer

What RAG actually does

Retrieval-Augmented Generation grounds an LLM's answer in your own documents instead of its training data — retrieve the relevant pieces first, then hand them to the model as context.

🔎

Retrieve

Turn the question into a vector, search a document index, get back the most relevant chunks.

🧩

Augment

Stuff those chunks into the prompt as context — the model reads them like a citation packet.

✍️

Generate

The LLM writes an answer grounded in that context and cites which chunk it used.

Under the hood

The pieces worth understanding

Why one model for dense and sparse — bge-m3›
Dense vectors capture meaning ("split URL test" ≈ "A/B redirect test"), sparse vectors capture exact terms (a JIRA key like VWO-1042 needs to match literally, not semantically). bge-m3 produces both from a single forward pass, so you get keyword precision and semantic recall without running two separate embedding models.
Reciprocal Rank Fusion — combining two rankings fairly›
Dense and sparse search return two differently-scaled ranked lists. Instead of trying to normalize their scores, RRF only looks at rank position:
score(doc) = Σ 1 / (k + rank_in_list)
A chunk that shows up near the top of either list gets a high fused score; one that shows up near the top of both wins outright. k=60 (a standard default) smooths out noise from rank 1 vs rank 2 being nearly identical in relevance.
Why rerank after already fusing two searches?›
Dense/sparse search score the query against a chunk independently and fast — that's why they can scan thousands of chunks. A cross-encoder reranker (bge-reranker-v2-m3) reads the query and each candidate chunk together in one pass, which is far more accurate but too slow to run on the whole corpus. So: cast a wide net with hybrid search (top 20), then spend the expensive step only on those 20 candidates to pick the true top 4.
Query rewriting — searching for what they meant, not just what they typed›
"cross-browser split test bug" and "A/B test fails on Safari" can describe the same underlying test case without sharing a single keyword. An LLM generates a few alternate phrasings of the question before retrieval, each one searched independently, and the results are merged — trading one extra LLM call for a meaningfully wider net.
Qdrant embedded mode — a vector DB with no server to run›
Qdrant normally runs as a server (Docker), but its Python client also runs it in-process, persisting to a local folder — same API, same named dense+sparse vectors and payload filtering, zero infrastructure. Good enough for a demo at this scale; swap in QDRANT_URL to point at a real server with no code changes.
Behind the build

How this got built: vibe coding, in practice

The whole app — pipeline, UI, test data, this page — came from a single markdown spec handed to Claude Code, then iterated against the real constraints of the machine it had to run on.

1. Write the spec, not the code

A prompt.md describing the pipeline, the tech choices, and what the UI should show per page — intent and shape, not implementation.

2. Reconcile the spec with reality

The spec assumed Openrouter; the machine only had a Groq key. It assumed a fresh environment; the machine was pinned to Python 3.8. Both got resolved by checking what actually existed before writing code that would assume otherwise.

3. Build the pipeline as swappable modules

Chunking, embeddings, vector store, reranking, and the LLM calls each live in their own file — so bge-m3 or Qdrant can be swapped later without touching the Flask routes.

4. Make the pipeline visible, not just correct

Every stage streams its own progress over Server-Sent Events, so ingest and chat both render as a live tracker instead of a spinner.

5. Generate a realistic corpus instead of hand-writing one

5,000 Jira-shaped VWO test cases, synthesized deterministically across ~27 product modules × browser/device/role variants — enough real structure to make hybrid retrieval and reranking actually show their value.

6. Verify the golden path in a real browser

Upload → ingest → chunks → chat, driven end-to-end before calling it done.
